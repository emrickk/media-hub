## 2. What changes, at product level

A pitched card today: cover, title, shape, synopsis, the case, sealed
prediction, verdict buttons. That is a title-thrower with a good argument.

A pitched card after this change also answers, per candidate:

| section | content | applies to |
|---|---|---|
| **entry** (从哪里开始) | where to start, why *that* point, and a cheap exit test ("watch these 2; if neither lands, drop it guilt-free") | episodic works — required when > 1 season or > 13 episodes; films skip it |
| **inside** (里面有什么) | 2–3 concrete moments, devices, or dynamics, spoiler-light; up to 2 quotes, each ≤ 15 words, attributed to character/show | all candidates |
| **reception** | one line of third-party standing (awards, consensus reputation) | all candidates, omitted when not known at high confidence |

The hook must connect to the **profile document**, not to genre labels —
same rule as the case ("this show's cold-open structure matches what the
profile says about X", never "you like animation").

## 3. Source decision: generated, not searched

Per the feedback: enrichment is produced from the **model's own knowledge**
of the work, in-session, during dossier building. No per-candidate web
research. Consequences:

- **Latency:** ~zero added network. The only fetches remain the ones the
  pipeline already does (pool evidence, TMDB shape/reviews).
- **Cost:** tokens only, and only for shortlist finalists (~8/run), never
  the whole pool sweep.

### 3a. The honesty contract (load-bearing — this is what keeps generated
enrichment from being confident noise)

1. **Basis labels.** Every enrichment block carries `basis`:
   `"model-knowledge"` or `"fetched-evidence"`. Stored always; the page may
   render it subtly. A claim's provenance is never ambiguous in the record.
2. **Falsifiable anchors.** An entry recommendation must name checkable
   things — season/episode numbers, episode titles, character names. Vague
   unfalsifiable praise ("the later seasons are great") is a contract
   violation, not a style problem.
3. **Thin-knowledge degradation.** For works the model knows only thinly
   (obscure, non-English, niche), the block must say so
   (`knowledge: "thin"`) and degrade to shape-based guidance ("episodic,
   any entry works; S1E1 is safe") **instead of inventing specifics**. An
   overdetailed entry claim about an obscure work is the fabrication
   signature the critic is told to hunt.
4. **Recency rule.** For works released near or after the model's training
   cutoff, model knowledge is presumed unreliable: enrichment must lean on
   fetched evidence already in the dossier, and say when it can't.
5. **Spoiler discipline.** Tease setup, never resolution.
6. **Quote and attribution caps.** ≤ 2 quotes per card, ≤ 15 words each,
   attributed to character/show. **Never** attribute an invented sentence
   to a real named critic or publication; reception claims stay at
   aggregate level ("won the Emmy", "widely considered its peak") and only
   at high confidence — when unsure, omit rather than hedge.

### 3b. How fabrication gets caught

The verdict loop already exists; enrichment plugs into it. A user report
that a quote doesn't exist or an episode pointer is wrong is a **critical
defect**: logged via `calibrate.py` against the engine (not the user), and
the offending pattern (e.g. quotes on thin-knowledge works) gets tightened
in the contract. Spot-checks are cheap because of rule 2 — anchors are
checkable by construction.

## 4. Layer placement — engine vs instance

This design was triggered by user feedback, but almost none of it is about
this user. Placement, explicitly:

**Engine layer (SCOUT.md / CRITIC.md — user #2 gets these for free):**

- **Version-identity rule.** A rating attaches to an *execution*, not an
  IP. Before an analogy or a kill cites a rated title, the scout must
  resolve WHICH version the row is (year + kind + review text) and match it
  to the version the argument needs. A low rating on one version leaves
  other versions **untested, not condemned**. The general class, enumerated
  so the rule is recognized beyond the instance that exposed it:
  remake vs original · live-action vs animation · US vs UK/regional
  versions · reboot vs continuation · per-season drift (a franchise's S1
  verdict does not bind S8) · adaptation vs source medium.
- **Entry-point requirement** for long episodic works, with the honesty
  contract above. Any user needs an on-ramp into a 100-episode show; which
  on-ramp is personal, that one is needed is not.
- **Enrichment schema + critic's judging duties** (§5, §6).

**Instance layer (engine_priors / README):** nothing new. The five priors
recorded earlier today (appetite vs rating, recency, external-rating
signal, horror, doc-fatigue) stay where they are — those are genuinely
about one user's reactions.

*(Correction on the record: the previous turn proposed "version-not-ip" as
a user prior justified by a TASTE.md quote. Wrong layer — it is an engine
rule and this design places it there.)*

## 5. Schema — `dossier.enrichment`

One new block per dossier. No DB migration; it is stored inside the
existing `dossier` JSON.

```json
{
  "enrichment": {
    "knowledge": "rich | thin",
    "basis": "model-knowledge | fetched-evidence | mixed",
    "entry": {
      "start_at": "S8E1 \"Good Times with Weapons\"",
      "why": "argued from the work's own structure AND the profile",
      "exit_test": "watch these 2 episodes; neither lands → drop it",
      "applicable": true
    },
    "inside": {
      "moments": [
        "2-3 concrete, spoiler-light moments/devices/dynamics"
      ],
      "quotes": [
        {"text": "≤15 words", "speaker": "character, show"}
      ]
    },
    "reception": "one aggregate-level line, or omitted"
  }
}
```

Field rules:

- `entry.applicable: false` + no `start_at` for films and ≤1-season works.
- `knowledge: "thin"` forbids `quotes` and episode-specific `start_at`.
- `moments` must be concrete enough to falsify (name the device, the
  character, the situation); marketing mush is a critic sendback.
- Every field optional-by-honesty: an empty section stated plainly beats a
  filled section invented.

## 6. Critic contract additions

The critic judges enrichment like any other dossier claim:

- **New sendback grounds:** ungrounded entry (no anchors); generic mush in
  `moments`; episode-level specificity on a `knowledge: "thin"` work;
  quotes present on a thin work; a named-source citation in `reception`;
  a hook argued from category labels instead of the profile.
- **Version-checked analogies:** any `history_analogues` entry citing a
  rated title must state the version match (or explicitly flag a version
  gap). An analogy resting on the wrong version is `kill_rule: fact`.

The critic's blindness is untouched: enrichment is dossier content, not
search-effort narration.

## 7. Render

Three additions to the card in `render.py`, all tolerant of absence:

- 「从哪里开始」 — `entry.start_at` + `why` + `exit_test`.
- 「里面有什么」 — `moments` as a short list; quotes styled as quotes.
- Reception as one muted line near the aggregates.
- `knowledge: "thin"` renders a small honest marker rather than hiding.

## 8. Future fields (deliberately out of scope now, per "will be included
in the further")

- Per-episode viewing maps ("watch these 9 of S1's 22").
- Verified quotes from a local subtitle corpus (the `subtitle-downloader`
  project could feed this — zero web at recommend-time).
- Trailer / clip links (needs web; conflicts with the latency decision —
  revisit only if asked).
- Cross-run caching of work-general enrichment into `candidate_pool`
  (split personal hook from work-general entry; not done in v1 because
  `evidence` currently means *fetched* material and mixing generated
  content into it would muddy raw-first provenance).

## 9. Risks, honestly

1. **Fabrication is the #1 risk.** Mitigations in §3a/§3b; residual risk
   accepted consciously in exchange for latency. Revert criterion: if two
   enrichment fabrications are user-reported in any five consecutive runs,
   quotes and episode-specific claims get suspended pending a verified
   source (subtitle corpus or fetched episode data).
2. **Token cost per run** grows by roughly one enrichment block × 8
   finalists. Acceptable; enrichment only for finalists.
3. **Overfit hooks.** A hook that name-drops the profile too literally
   reads as pandering. The case-writing rule already covers register;
   enrichment inherits it.
